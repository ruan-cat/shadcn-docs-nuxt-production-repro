## 结论

✅ **R40 判定：candidate。`--force` 确实强制重跑全部 4 个 task，但「fresh 产物 ≠ cache-hit 产物」这一核心信号已定案；「真冷缓存」臂（隔离 `.turbo/cache` 后从零构建）本轮未执行。**

1. **`--force` 生效且代价明确**：`0 cached, 4 total`，4 个 task 全部真实执行，本机耗时 **165.9s**（对比 cache-hit 路径的 138ms / 1s，约 **1200 倍**）。
2. **fresh 路径与 cache-hit 路径产物不等价**（核心信号命中）：manifest4 vs manifest1 = 356 行差异（178 对路径 + 15 个同路径内容变化）。**且 fresh 与 fresh 之间也不等价**：manifest6 vs manifest4 = 356 行差异。⇒ 本仓构建**内容幂等、字节非幂等**。
3. **「被缓存遮蔽的构建失败」在本仓未以「失败」形式出现**：fresh 重跑 exit 0、4/4 成功、Content 探针 13/13 PASS。⇒ 被 cache 遮蔽的**不是失败**，而是**产物的不确定性**——若用 cache hit 产物做验收，会把「每次重跑字节不同」误判为「构建稳定」。这正是 F35「不允许只用 cache hit 作为验收证据」在本仓的具体落点。
4. **`--force` ≠ 冷构建（已实证）**：#4 全量重跑后紧接的 #5 仍为 `4 cached / 138ms FULL TURBO`。`--force` 只强制重跑 task，**不清 turbo cache、不清 tsbuildinfo**。⇒ 「fresh」在本仓有两种语义，必须区分：
   - **强制重跑语义**（`--force`）：本实验已完成，等价于「不读缓存地重跑一次」。
   - **冷缓存语义**（隔离 `.turbo/cache` 后构建）：**本轮未执行**。
5. **未执行「冷缓存臂」的理由（如实记录）**：隔离 `.turbo/cache` 会抹掉 R42–R44（构建顺序与并行矩阵）所需的缓存对照锚点；本仓 `turbo.json` 的 `outputs` 为通配，缓存条目内含历史遗留的 `.vercel/output/**`，重建后行为可能与首轮不可比。故本轮以「强制重跑臂 + 三次重跑互不相同」覆盖「fresh 语义」，冷缓存臂留待 R42–R44 完成后单独执行。

## 关键发现

1. **fresh 重建 ≠ 产物同一**：本仓两次「同代码、同依赖、同命令」的真实重跑，产物字节不同但内容等价。差异根因见 R39「关键发现 2」。
2. **`--force` 的成本已被量化**：166s vs 138ms（Windows）。Linux control 侧 `pnpm build:fresh` = 1m18.339s（`Cached: 0 cached`）。⇒ 本仓 CI 与本地若都声称「fresh」，需在 PR body 中写明是「强制重跑」还是「冷缓存」。
3. **`--force` 不会清理增量状态**：`packages/shared-core` 的 build 脚本已带 `--incremental false`（契约 `tests/build-idempotency.test.mjs` 固化），故 TS 增量陷阱已被隔离；但 **turbo 缓存本身不被 `--force` 清理**。
