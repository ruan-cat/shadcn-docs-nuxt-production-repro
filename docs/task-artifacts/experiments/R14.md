## 结论

⚠️ verified（部分命中）—— 按 SOP 干净重测，`experiment/r14` 分支（blanket Nitro inline）install / build:packages 全绿（exit 0），但 **`docs build` 在默认 heap（约 4 GiB）下于 Nitro server 打包阶段 `exit 134`（SIGABRT），V8 报 `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`，heap 峰值 ~4.1 GiB**。受控对照：注入 `NODE_OPTIONS=--max-old-space-size=8192` 后重测，`nuxt build` `exit 0`（~131s），standalone `.output` 启动 `Listening on http://[::]:3000`、HTTP 200（107125 bytes）且响应体含 `生产级复现实验室` 真实内容。

**判读**：与 R06/R07/R08/R10/R12（干净全绿、首轮失败为纯污染伪信号）不同，R14 在干净环境下**并非全绿**——其单变量（blanket Nitro inline）确实将 Nitro server bundle 的 Rollup working set 放大到越过 4 GiB 默认 V8 堆上限，从而**复现 F15 假设的默认 heap OOM**。但这属于**资源约束型 OOM，而非构建逻辑故障**：提升 heap 上限即可正常构建，变量本身未引入错误依赖或打包错误。因此首轮 `exit 1 + Invalid URL` 确为污染态伪信号（应判废），但干净重测揭示的真实结论是"默认 heap OOM 可复现、充足 heap 可构建"，与 F15 的"放大 working set 致 OOM"机制一致。

## 关键发现

- **R14 是系列中首个"干净态非全绿"**：R06–R12 干净重测均全绿（首轮失败纯属污染伪信号），而 R14 干净态默认 heap 下复现 `exit 134` OOM。机制区别——污染态伪信号表现为 `exit 1 + Invalid URL`（依赖解析层错误），R14 的 `exit 134` 是 V8 原生 `SIGABRT`（heap OOM），二者完全不同，故 R14 的失败是**变量真实效应**，非污染残余。
- **blanket Nitro inline 真实放大 server bundle 内存**（印证 F15）：默认 4 GiB heap 不够，需 ≥8 GiB 方可构建；基线 main（R23/R24 测量约 3.5–4.0 GiB 峰值）在默认 heap 下尚可完成，说明该变量确实把水位推过上限。
- **资源约束 vs 逻辑故障的判定纪律**：OOM 类失败须用"提升 heap 上限"受控对照证伪；本例对照后翻转为绿，证明非逻辑故障，但变量确有内存成本。这与 SOP "疑似伪信号：用受控对照证伪"一致，但结论不是"判废"，而是"部分命中 / 内存回归"。
- **安全提醒（无关变量）**：`pnpm install` 的 `apps/docs prepare`（`nuxt prepare`）在恢复 main 时因 WorkBuddy 沙箱 `node-safe-delete-shim` 拦截批量删除 `.nuxt/dist`（507 文件 > 阈值 50）而报 `ELIFECYCLE`，与 R14 无关；移走陈旧 `.nuxt` 后重装 `exit 0`。属环境守卫，非实验结论影响因素。
