## 前置判断记录（B1 调查，关键）

> 调查结论：mermaid 是 shadcn-docs-nuxt@1.1.9 的声明依赖，通过**全局客户端插件 + markdown 渲染组件**拉入客户端执行路径；主题层 `vite.optimizeDeps.include` 只预优化 `debug`，**未**预优化 mermaid/dayjs/@braintree/sanitize-url（与任务 hint「eams 同 extends 主题需手动加，本主题未预优化」一致，已源码级证实）。

### 1. mermaid 依赖与版本

- shadcn-docs-nuxt `package.json`：`"mermaid": "^11.12.2"`（声明依赖）。
- lock 解析：`mermaid@11.17.2`，其 `package.json` 为 `"type": "module"`（ESM）。
- 四包传递链（lock 证据）：
  - `shadcn-docs-nuxt@1.1.9` → `mermaid@11.17.2`（pnpm-lock.yaml 依赖块 line 14596）；
  - `mermaid@11.17.2` → `@braintree/sanitize-url@7.1.2`（line 12910）、`dayjs@1.11.23`（line 12921）、`debug`（mermaid 依赖块内）；
  - 主题 `vite.optimizeDeps.include: ['debug']`（见下方第 3 点源码实锤）。

### 2. 触发机制（主题源码实锤，非猜测）

- `plugins/mermaid.client.ts`：**全局 `.client` 插件**，`import mermaid from 'mermaid'`（静态引入）→ 把 mermaid + 其传递依赖（dayjs / sanitize-url / debug）拉入客户端构建图，并在 `defineNuxtPlugin` 中 `provide: { mermaidInstance: mermaid }`。
- `components/content/ProseCode.vue`：`const isMermaid = computed(() => language === 'mermaid' || parsedMeta.value.has('mermaid'))` → 当 markdown 出现 ` ```mermaid ` 代码块时渲染 `<MermaidRenderer>` 而非代码卡片。
- `components/content/MermaidRenderer.vue`：客户端 `onMounted` 经 `IntersectionObserver` 调用 `$mermaidInstance.render()`（来自全局插件）→ 实际执行 mermaid 解析，内部调用 dayjs / sanitize-url / debug。

### 3. 主题层配置实锤（optimizeDeps 缺口）

- 主题 `nuxt.config.ts`：
  ```js
  vite: {
    plugins: [tailwindcss()],
    optimizeDeps: { include: ['debug'] },  // 仅预优化 debug
  }
  ```
- 结论：mermaid / dayjs / @braintree/sanitize-url **不在** `optimizeDeps.include` —— 即任务 hint 所述「本主题未预优化」得到源码级证实。这恰是 F30 类 ESM/CJS 入口冲突的预期温床（dev 模式尤为敏感）。

### 4. 最终触发手段与理由

- **手段**：在 `apps/docs/content/1.guide/1.baseline.md`（路由 `/guide/baseline`，已在 prerender 种子内）末尾追加一个合法 ` ```mermaid ` flowchart 块。
- **理由**：① `ProseCode.isMermaid` 命中 → `MermaidRenderer.onMounted` → `$mermaidInstance.render()` 完整触发四包运行时路径；② 只改 content、不动 vite/nuxt 配置 → 12 项 `baseline-safety` 契约不受影响（main 无 `experiment.json`，无 forbidden pattern 引入）。这是用户拍板的单变量。

## 结论

**`verified`（收敛事实）+ `clean negative`（F30 复现）**：

1. **收敛事实 verified**：dayjs / debug / @braintree/sanitize-url 经 mermaid 传递依赖，四者 client 触发路径汇聚到 mermaid 一个导入图（lock 14596/12910/12921 + 主题源码实锤）。R30/R32/R33 由同一 mermaid 触发块覆盖，**无需三个独立实验**。
2. **F30 复现结论（clean negative）**：在当前 `shadcn-docs-nuxt@1.1.9` + `mermaid@11.17.2` + 生产 `node-server` 构建下，**插入 mermaid 触发块不会复现 F30 的 ESM/CJS 入口冲突**——mermaid 正常渲染为 SVG、hydration 完成、四包零入口错误。dev 模式仅呈现 Vite 426 依赖重优化循环（优化缺口的不同表现），亦非 F30 原文签名。
3. **归因（事实驱动，非猜测）**：生产构建由 Rollup 统一打包并对 CJS 依赖做正确 interop，故 mermaid 入口图（含 CJS 的 dayjs / sanitize-url）无入口冲突；F30 描述的「ESM/CJS 入口冲突打断 hydration」在当前生产构建链路中**未由 mermaid 触发块触发**。若要在本仓稳定复现 F30，相关轴应为「Vite dev optimizeDeps 缺口」或「外部化 mermaid 的构建」而非单纯生产内容触发，属后续独立实验方向。

## 关键发现

- B1：主题 `vite.optimizeDeps.include: ['debug']` 仅预优化 debug，mermaid/dayjs/sanitize-url 未预打包（源码实锤，印证收敛 hint）。
- 生产构建下 mermaid 内容触发 = 干净渲染（无 F30），与 F30 原文签名不符 → F30 在当前链路属未复现（clean negative），非「已证实存在」。
- 404 噪音源：`/api/_content/query?_path=/guide` 索引缺页，与四包无关，已排除。
- 横向价值：mermaid 触发机制（全局 `.client` 插件 + `ProseCode.isMermaid` → `MermaidRenderer.onMounted`）已源码级厘清，可作为后续 docs mermaid 相关回归的基线。
