## 结论

✅ **verified**——R24 完成（2026-10-19）：4608 MiB heap 档位下 docs build 绿（exit 0 / 160.0s，与 R23 160s 持平），OOM 未复现。峰值 WS 3902.9 MB vs R23 3599.4 MB = +8.4%，在 ±10% 判据内 → 证明**构建水位由构建图决定，非 heap 上限**（V8 按需扩堆，提升上限不改变实际水位）；lazy GC 显著抬升行为（>10%）未出现。本机默认 heap 实测 4144 MiB（Node 22 大内存自适应，非固定 4096），当前水位距默认上限余量约 12%，与 FINDINGS #14 "余量 13.2%" 一致量级。

## 关键发现

1. **heap 档位验证须用实测而非理论值**：注入 `--max-old-space-size=4608` 后 `v8.getHeapStatistics().heap_size_limit` 实测 4882169856 B（≈4656 MiB），较理论 4831838208 B 多 48 MiB（V8 向上对齐粒度）；且本机默认 heap 实测 4345298944 B（≈4144 MiB），非文献常引的 4096 MiB。后续 R25/R26 档位验证照此用 `getHeapStatistics` 实测留证。
2. **.output 冒烟必须验证 server log 的 `Listening` 行**：首轮冒烟三断言虽全 200，但 server log 尾部实为 `EADDRINUSE`（errno -4091）——3000 被此前实验遗留孤儿 server（PID 16964，`node apps/docs/.output/server/index.mjs`，创建于本轮 build 之前）占用，200 全部来自旧产物进程，证据作废。定向终止孤儿后重测，方得本轮产物有效证据。教训沉淀：冒烟流程先查端口监听者 + 验证 `Listening` 行，再发断言请求。
