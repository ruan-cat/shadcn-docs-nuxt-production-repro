## 结论

✅ **R39 判定：verified。cache hit 与 fresh 重跑产出「内容等价但字节不等价」的产物；且 turbo 缓存的还原行为受工作区产物目录状态支配，而非仅由 task hash 决定。**

1. **cache hit 是严格的字节级还原。** 连续两次 `pnpm build`（#1 → #2）产物清单 1792 个文件**逐行完全相同**（diff = 0 行），包含所有 sha256。缓存还原的是**同一份字节**，不是「重新构建出的等价物」。
2. **fresh 重跑与 cache 还原的产物字节不等价。** #4（`--force` 全量重跑）与 #1/#2 的差异为 356 行 = 178 对路径新增/消失 + 15 个同路径文件内容变化。**每次真实重跑都会产生不同的字节**（#3/#4/#6 三次重跑之间互不相同）。
3. **差异已被完整归因，分两类，且**「内容」全部等价：
   - **构建指纹类（每次必变，可预期）**：`@ztl-uwu/nuxt-content` 的 `buildIntegrity = Date.now()` → 写入 Content 路由名（`cache.<ts>.json`、`search-<ts>`）与 `runtimeConfig`；Nuxt `buildId` UUID（`public/_nuxt/builds/latest.json`）；`nitro.json` 的 `date`；`nitro.mjs` 内资源 `mtime`。
   - **枚举顺序不确定性类（实质差异，反复出现）**：`server/chunks/build/server.mjs` 内嵌的 lucide 图标集合 JSON **key 顺序**在 m1/m4/m6 之间持续变化（`languages` → `check` → `sun`），`styles.mjs` 内 `error-404` / `error-500` 条目顺序互换。同长度替换（6335/6335、198815/198815 字节），**集合内容相同、仅顺序不同** → 传导为 `public/_nuxt/*.js` 的内容哈希文件名变化 → 178 对路径新增/消失。
4. **因此「产物字节相同」在本仓不是可达验收门。** 任何形如「两次构建产物必须逐字节相同」的门在此仓**必然假红**；正确判据是「**构建指纹 + 枚举顺序归一化后内容等价**」。
5. **cache hit 并非必然，取决于工作区产物目录状态**（本实验最具实践价值的发现）：
   - `.nuxt` 目录**参与** turbo task hash：#6 把 `apps/docs/.nuxt` 改名移走后，docs 的 hash 由 `5f736996212e114e` **变为** `032bab828abe7d0e` → 必然 miss。
   - `.output` 目录**不参与** hash（#3 中 hash 未变），但**缺失时 turbo 无法完成缓存还原** → 降级为 miss 并重新执行。
   - 无 `.nuxt` 的三个 task（`shared-core`/`ui`/`api`）在 `dist`/`.output` 被改名移走后**仍能 hit 并还原产物**。
   - ⇒ **docs task 的缓存还原同时要求 `.output` 与 `.nuxt` 两个目录原位存在且内容匹配**；只清一个就不成立。
6. **`.turbo/cache` 在仓库根，不在 `node_modules` 内**（实测 207 个子项）。⇒ 隔离 node_modules（AGENTS.md §0.5）**并不能**清空 turbo 缓存；「干净环境」与「冷 turbo 缓存」是两件事，此为既有 SOP 的盲区。
7. **首次建立 Linux 计时基线**：main 的 Linux `pnpm build:fresh` = **1m18.339s**（4 successful / 0 cached）。此前仓内所有计时基线（R20 213s、R23–R26 160–161s）均为 Windows，Linux 与 Windows 相差约 3 倍量级（Windows 本轮 166–185s）。

## 关键发现

1. **「cache hit 掩蔽 fresh 失败的对照证据」信号命中（verified）。** 用 cache hit 的产物（1s、138ms）当验收证据，会掩盖「真实重跑产物每次字节不同」这一事实——即掩盖了构建的**非幂等性**。二者内容等价，但**不可互换为 fresh 证据**（F35 原则在本仓的具体体现）。
2. **本仓构建非幂等（内容等价 / 字节不等价）**：根因有二——(a) Content `buildIntegrity` 时间戳指纹；(b) **模块求值顺序不确定性**传导到内联 JSON 的 key 序与 chunk 哈希文件名。（b） 是本轮首次定位，属横向发现。
3. **turbo 缓存还原的三条机制事实**（补 AGENTS.md §0.5 盲区）：
   - 缓存落点 = 仓库根 `.turbo/cache`（**不在 `node_modules` 内**）；
   - `.nuxt` 参与 task hash，`.output` 不参与但缺失会阻断还原；
   - `turbo.json` 的 `outputs` 是**通配**（`dist/**`、`.nuxt/**`、`.output/**`、`.vercel/output/**`），会把历史遗留的 `.vercel/output/**` 一并打包进缓存条目。
4. **`--force` 不是冷构建**（承 R31-family 记录）：`--force` 只强制重跑 task，**不清 turbo cache、不清 tsbuildinfo**；#4 全量重跑后紧接的 #5 仍是 `4 cached / 138ms FULL TURBO`。要真冷构建需额外隔离 `.turbo/cache`——本轮未做（会抹掉 R42–R44 所需的缓存对照锚点）。
5. **Linux 与 Windows 构建耗时量级差异约 3 倍**（1m18s vs 166–185s），此前仓内无 Linux 计时，跨平台耗时对照此前一直缺基线。
