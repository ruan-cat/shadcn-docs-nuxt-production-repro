### ⚠️ 已识别的三类风险（启动前必须先决策，不得在 PR body 里含糊）

- **R-1（h3 v2 双实例）**：`nitro@3.0.260610-beta` 把 h3 **精确钉死**在 `2.0.1-rc.22`；而 R45 的 docs 链需 h3 v2 **稳定版** `2.0.8`。若 apps/api 不动 → 同一 lock 内出现 **h3 v2 的两个不同实例**（`2.0.8` 与 `2.0.1-rc.22`），二者虽同为 v2，但 rc 与 stable 的 API 存在差异风险。
  - **方案 α（严格单变量）**：apps/api 保持 `nitro@3.0.260610-beta` 不动 → R45 只迁 docs；但**必须**在 PR body 明确声明「h3 v2 双实例」为已知残留风险，不得沿用旧表述「F05/F06 的 sibling 跨世代拓扑前提已消失」（该表述**不准确**：前提并非消失，而是**转移**）。
  - **方案 β（世代对齐）**：apps/api 同时升到 `nitro@3.0.261029-rc`（依赖 `h3 ^2.0.8`）→ docs 与 api 共用同一 h3 v2 实例，消除双实例；但**变量面扩大**，须在 PR body 的「唯一变量」栏显式声明「docs 与 api 同代迁移」为同一语义变量。
  - **本档不预选**：两方案的取舍属产品/风险决策，启动时须先定并写入 PR body。
- **R-2（override 低于主题声明最低版——基线既有的既存矛盾）**：`shadcn-docs-nuxt@1.1.9` 自身声明 `nuxt-og-image ^5.1.13`，而 root `pnpm.overrides` 钉在 `5.1.9`（**低于主题声明的最低版**）；1.2.2 则声明 `^6.5.0`，差距更大。⇒ R45 必须同时解掉这个既有矛盾，否则「迁移后全绿」不能证明迁移正确（override 会强制拉回错误版本）。
- **R-3（`pnpm-workspace.yaml` 的 4 条 h3@1.15.11 packageExtensions 必须整体删除）**：实测 `@ztl-uwu/nuxt-content@2.14.1` **自身不声明 h3 依赖**（h3 由 packageExtensions 注入）→ 继续钉 `h3@1.15.11` 会在 Nuxt 4 链路上**人为制造 h3 v1/v2 反向世代错配**。这 4 条必须删除而非改版本。

### 目录结构决策（Nuxt 4 `srcDir` 语义——实测源码依据）

- `@nuxt/schema@3.21.2/dist/index.mjs:859-895`：v4 模式下若 `apps/docs/app/` 存在且**含真实内容**（`router.options*` / `spa-loading-template.html` 除外），`srcDir` 翻转为 `apps/docs/app` → 根级 `middleware/`、`components/`、`app.config.ts` **全部孤儿化**。

## ✝️ 订正：启动前「R-3 前提」被实测证伪（2026-10-30 执行期追加，不改写上文原文）

- **被证伪的前提**：「Nuxt 4 链必然是 h3 v2 世代 ⇒ content 2.14.1 会把 h3 带到 v2 ⇒ 必须删 4 条 h3@1.15.11 packageExtensions，否则人为制造反向世代错配」。
- **实测事实**：
  1. `nuxt@4.6.3` 的服务端运行时仍是 **Nitro 2.13.5 + h3 1.15.11（v1 世代）**——构建日志明写 `Nuxt 4.6.3 (with Nitro 2.13.5, Vite 8.3.5 and Vue 3.5.44)`；`nitropack@2.13.5` 的 `dependencies.h3 = ^1.15.11`；npm 上**最新**的 `@nuxt/nitro-server@4.6.3` 同样声明 `nitropack ^2.13.5` + `h3 ^1.15.11` ⇒ **不存在任何「Nuxt 4.x 配 Nitro v3 / h3 v2」的官方组合**。
  2. `@ztl-uwu/nuxt-content@2.14.1` **自身不声明 h3**（dependencies / peerDependencies 均无），其 runtime 只 import `createError` / `getQuery` / `getCookie` / `defineEventHandler`（v1/v2 都有），**完全不使用 `event.path` / `event.url`**（仅 `query.js:18` 用 `statusMessage`）⇒ **content 2.14.1 对 h3 世代不敏感**。
  3. 首版实现（h3 升 `2.0.8` + 3 处 `event.url.pathname` 迁移）**构建失败**：client/server 构建通过（`Server built in 6149ms`）但 prerender 全部 500，根因 `Cannot read properties of undefined (reading 'pathname')`——`event.url` 在 h3 v1 运行时不存在。
- **处置**：**h3 保持 1.15.11 不动**；`apps/docs/server` 下 3 处 h3 v2 迁移**全部回退**；4 条 packageExtensions 的**删除动作保留**，但**理由改写**为「Content 2.14.1 自身不声明 h3，删除后让它跟随应用声明的 h3 世代」；`experiment.json` 的 `expected` 中**移除 h3**。
- **结论**：**h3 不是 R45 的可迁移轴**；R-2 的动作**保留且必要**（root override `nuxt-og-image` 5.1.9 → 6.10.2，主题 1.2.2 声明 `^6.5.0`）。

- **对既有结论的影响（推论，非直接取证）**：R42/R43/R44 三轮的 `probe:content` 13/13 PASS **不受影响**——这三轮各自构建的指纹互不相同，而**指纹路由断言是通过的** ⇒ 应答者必为同一构建（若被别的构建应答，带旧指纹的 `cache.<ts>.json` 必然 404）。

### 真缺陷的机制（产物级取证；control = `.output.stale-r44c`，R45 = `.output`）

1. **control 产物把已解析内容打包进了产物，R45 没有**：
   - control `server/chunks/_/nitro.mjs:3450-3468` 有 **5 条** `nitro:bundled:cache:content:*` 服务器资产（`content-index.json` + 4 条 `parsed:content:*`，etag 长度 `0xb5b` = 2907 B，与 control 的 JSON 体积一致）；
   - R45 产物**一条 `nitro:bundled:` 都没有**。
2. **构建期写入内容形态不同**：
   - control `.nuxt/content-cache/` = **5 个文件**：`content-index.json`(184 B) + `parsed/content/*.md` = **已解析 JSON**（`{"parsed":{"_path":"/","title":"生产级复现实验室","body":{"type":"root","children":[…]}}}`，2907/2245/5548/1478 B），mtime = 各自构建时刻（r42 17:58:20 / r44c 18:27:32 / R22 worktree 19:01:33）；
   - R45 `.nuxt/content-cache/` = **4 个文件**，`parsed/content/*.md` = **原始 markdown**（851/724/459/277 B，与源文件 `apps/docs/content/**` 体积一一相等），mtime 19:17:42 = 构建时刻，且**缺 `content-index.json`**。
3. **运行时不会兜底解析**：`dist/runtime/server/storage.js:136-139` 源码是 `if (isProduction && cached) { return cached.parsed; }`；两版产物里该判定都被打包成 `if (cached) { return cached.parsed; }`（`isProduction` 被常量折叠）⇒ **缓存里是原文时 `cached.parsed` 是 `undefined`，运行时直接返回 undefined**，不会现场解析。
4. **content 包无责**：2.14.1 与 2.13.9 的 `dist/module.mjs` **逐行相同**（`Compare-Object` 仅 `const version` 一行不同）；整包 143 → 158 文件，差异**只有新增的 `*.d.vue.ts` 类型声明**，`dist/runtime/**` 运行时文件**全部相同** ⇒ **content 升级不是根因**。
5. **nitro 2.13.4 → 2.13.5**：`dist/rollup/index.mjs` 的 `bundledStorage` 注入代码（2.13.4 `:1593-1628` vs 2.13.5 `:1598-1633`）与 `createStorage`（`storage` + `devStorage` 合并）逻辑**一致**；但 `dist/core/index.mjs` **整体重构**（`snapshotStorage` 由 2.13.4 的 `:1083` 漂移到别处，整体行号偏移 ≈30 行）⇒ **未逐行定位到具体改动点**（登记为待归因）。
6. **content 模块自身的写入行为**（2.13.9/2.14.1 相同）：`dist/module.mjs:640-667` 的 `build:before` 钩子把 `content:source:*` **原样**拷进 `cache:content:parsed:*`；配合第 3 条 ⇒ **一旦缓存位里是未解析原文，运行时就永不解析**（R45 实测正是如此）。control 为何在**相同 module 代码**下写入的是 JSON，本轮**未逐行归因**。

**❌ R45 判负（阻断级）：Nuxt 4 同代迁移在「生产内容库」这一维度上不可用。**

- 迁移本身**能构建**：docs 构建 exit 0（54s，prerender 11 routes），`probe:closure` exit 0，契约 15/15。
- 但**产物内容库为空**：Content API 的 `query` / `cache.<ts>.json` / `search-<ts>` / `navigation` 全部返回**空集合** ⇒ **站点发布后文档页没有内容**。这比 F47 的「200 假阳性」更严重——F47 是**状态码骗人**，本缺陷是**数据真的没有**。
- 判负点落在**「Nuxt 4 世代整组迁移」这一变量本身**：
  - **不是 content 升级**（2.13.9 → 2.14.1 的 `dist/module.mjs` 逐行相同，整包差异只有类型声明）——已证伪；
  - **不是 h3**（h3 全程保持 1.15.11，首版 h3 v2 迁移导致的 prerender 500 已回退）；
  - **也不是探针误报**（干净端口重跑复现，且失败形态是「200 + 空集合」而非「404」）。
- **未归因部分（诚实登记）**：control 为何在**相同的 module 代码**下把**已解析 JSON** 写进 `cache:content:parsed:*`，而 R45 写入的是原文——差异必在 Nuxt 4 / Nitro 2.13.5 的构建时序或 `snapshotStorage` 重构处，本轮**未逐行定位**。

## 关键发现

1. **【FINDINGS #28】Nuxt 4 同代迁移导致生产内容库为空（阻断级）**——产物里既没有 `nitro:bundled:cache:content:*` 服务器资产，`cache:content:parsed:*` 里也只有未解析原文；运行时 `getContent` 命中缓存即 `return cached.parsed`（原文 ⇒ `undefined`）⇒ 内容为空。取证见本文「真缺陷的机制」6 条。
2. **【FINDINGS #28】探针在端口被占用时会静默复用 stale server（验收工具缺陷）**——`probes/content-smoke.ts` 的 `waitForServer` 不校验应答者身份；本轮因此把 R22 遗留 standalone 的响应当成 R45 的结果（11 PASS / 2 FAIL），**整轮判废**。⇒ 任何「固定端口起服务再打」的验收都有**假 PASS / 假 FAIL 双向风险**，必须加「端口占用即拒绝」或「应答者身份校验」。
3. **【FINDINGS #28】「Nuxt 4 = Nitro v3 / h3 v2」的前提不成立**——`nuxt@4.6.3` 的服务端运行时仍是 **Nitro 2.13.5 + h3 1.15.11（v1 世代）**；npm 上最新的 `@nuxt/nitro-server@4.6.3` 亦然 ⇒ **不存在 Nuxt 4.x 配 Nitro v3 / h3 v2 的官方组合**；`content@2.14.1` 自身不声明 h3 且不用 `event.path`/`event.url` ⇒ **h3 不是 Nuxt 4 迁移的可迁移轴**。
4. **【FINDINGS #28】content 模块 `build:before` 的写入与运行时「命中缓存即返回」相冲突**——`build:before` 把**原文**拷进 `cache:content:parsed:*`，而运行时 `getContent` 在生产下命中缓存就 `return cached.parsed`（不解析）⇒ **缓存位一旦被原文占据，内容库必然为空**。这是上游 content v2 的「构建期写入 / 运行期消费」契约缺口，在 control 被别的东西掩盖、在 R45 暴露。

## 后续建议（下一步的单变量设计）

- **R46（推荐，单变量）**：**control（Nuxt 3.21.2 / content 2.13.9）不动，只把 lockfile 里的 `nitropack` 从 2.13.4 单点 bump 到 2.13.5**（nuxt 3.21.2 的 range 允许）→ 重建 + 同样的 `probe:content` 断言。
  - 若同样出现空内容库 ⇒ **根因在 nitro 2.13.5**（与 Nuxt 4 无关）⇒ R45 的「Nuxt 4 世代迁移」可缩小为「nitro 2.13.5 迁移」这一更小的变量；
  - 若内容库正常 ⇒ **根因在 Nuxt 4 世代本身**（`build:before` 写入 / `snapshotStorage` 时序 / `bundledStorage` 快照）⇒ R45 维持判负，且需向 `@ztl-uwu/nuxt-content` 与 nitro 上游提 issue。
- **并行可做**：探针加固（FINDINGS #28）——「spawn 前检测端口占用则直接 exit 非零」+「就绪后校验应答者身份」，作为**独立于 R45 变量**的改动单独提交，并按「红绿差分自证」跑一次（占用态必须 exit 1）。
