## 关键发现

1. **R42↔R43 的差异残差与「顺序」无关**：三个配对（R42↔R43、R42↔R44、R43↔R44）的 docs 残差**恒为同一组 6 个文件**，签名完全一致；5 个同名文件归一化后**长度相等 + 字符多重集相等**（`styles.mjs` 逐行排序后亦相等）→ 属同内容异顺序的置换；第 6 个是携带指纹的 client chunk（其内容差异来自 lucide 图标 JSON key 序 + 压缩器局部标识符命名）。
2. **api 产物逐字节相同**：三轮 `apps/api/.output`（2 文件，`index.mjs` 均 62116 B）非 volatile 哈希零差异、路径集合一致、路由三条一致 → api 构建不受 docs 构建顺序与并发影响（其输入只有 `@repro/shared-core`）。
3. **峰值 WS 对顺序不敏感**：3599.4（R23 基线）→ 3619.2（R42）→ 3580.9（R43），全部落在 ±10% 噪声带内；内存水位由**构建图**决定，与执行顺序无关（与 R24「水位由构建图决定、非堆上限/非执行次序」的既有结论一致）。
4. **墙钟差异同样在噪声内**：R42 串行 164.6s（3.5 + 159.2 + 1.9）vs R43 串行 162.3s（5.7 + 1.9 + 154.7）——差 2.3s，且方向与「api 先跑反而更快」无关（api 仅 1.9s），属构建耗时本身的抖动。
5. **题面「4 项合取」在 docs 侧字面不可达（字节相同不是可达门）**：本仓 fresh 构建**内容幂等、字节非幂等**（构建指纹 + 枚举顺序不确定性，依据 FINDINGS #23），因此 R42/R43/R44 之间**只能判「内容等价」，不能判「字节相同」**。具体地，161 个 `public/_nuxt/<contentHash>.js` 的文件名本身由构建指纹派生，且 chunk 内部互相引用兄弟 chunk 名 → 指纹一变，文件名与内容同时变（级联）；故本轮采用分层判据并在 evidence 中**如实标注字面合取 FAIL + 内容等价 PASS**，不把「字节相同」当作可达判据。
6. **题面采样器的 `repoCount` 判据在本机恒为 0（探针口径失效，已修正）**：题面用 `Get-Process` 的 `.Path -like '*shadcn-docs-nuxt-production-repro*'` 识别「本仓进程」，而 `.Path` 是**可执行文件路径**（本机 node 位于 `D:\store\nvm-desktop\22.23.1\node.exe` 与 `C:\Users\pc\.nvmd\bin\node.exe`，**在仓库之外**）⇒ 永远命中 0 个进程。本轮补建 CIM `CommandLine` 口径采样器后得到 `cim_repoNodeCount=2`、`cim_maxWS_peak_MB=3563.9`、`cim_sum_peak_MB=3571.7`；**教训：计数恒 0 时先怀疑判据、再下结论**（详见 [R44](./R44.md) 关键发现 1）。
