## 3. 结论（verified，轴 A 范围内）

1. **键形态子机理成立（实测）**：Nuxt 3 生成 renderer `:390` 的抽取写入键 = 内联三元 `ssrContext.url === "/" ? "/" : …` → 根路由键 = **`"/"`** → unstorage 1.17.6 `itemKey`（`normalizeKey("/")` = `""` falsy）**抛错** ⇒ R46/R49 prerender 500；Nuxt 4 的写入实现迁入 `nuxt@4.6.3/dist/runtime/server/renderer/index.js`，键 = `getPayloadCacheKey(url)`（`:676-679`）→ 根路由键 = **`"/.json"`**（补 `.json` 后缀）→ `normalizeKey` 非空 ⇒ **同一 1.17.6 校验通过** ⇒ R45/R51 臂 2 构建全绿。同一校验、键形态定生死——**FINDINGS #33 发现 2 的排除法定案就此升级为代码级正向实锤，R49.md ✝️ 的「未做字节级对比」推断标注闭合**。
2. **异常包裹子机理否定（实测）**：Nuxt 3 生成产物 `:382`/`:390` 与 Nuxt 4 实现 `:267`/`:272` 的 `payloadCache.setItem` 均为**裸 await**（无 try/catch、无 `.catch`）⇒ Nuxt 4 不是靠吞异常规避的。附带精确化：Nuxt 3 `:382`（payload 直渲路由，键 = url 如 `/guide/_payload.json`）本身合法——R46/R49 报错栈落在 `:390:22` 而非 `:382` 的原因由此解释。
3. **payloadCache 实例链（实测）**：Nuxt 4 的 payloadCache = `runtime.prerender.payloadCache` ← `nitro-server@4.6.3` `utils/renderer/options.mjs:3,34` ← `utils/cache.mjs:10` `useStorage("internal:nuxt:prerender:payload")`（import 自 `nitropack/runtime`）⇒ unstorage 归位 **nitropack@2.13.5 → 1.17.6（有校验）**——Nuxt 4 的 payload 写入**确实穿过 1.17.6 校验**，键 `"/.json"` 合法故通过；不是换了无校验实例。
4. **#32 发现 5 表述订正（实测驱动）**：R45「内容库为空」与 unstorage 1.17.6 key 校验**无关**——content 侧 `prefixStorage` 是 content 自己 import 的 unstorage（2.13.9/2.14.1 归位均 1.17.5，无校验），且 cache id 非全斜杠，即使走 1.17.6 也不会抛。R45 内容空的真因仍在 content runtime 轴（**轴 B**，未做）。FINDINGS #32 发现 5 的「同一个根因、两种表象」已加 ✝️ 订正。
5. **世代布局差异（实测）**：renderer 模板 307 行（N3，payload 内联）→ 27 行薄壳（N4，`createNuxtRenderer("nuxt/internal/renderer")`）；独立 prerender bundle（`.nuxt/prerender/chunks/_/`）在 Nuxt 4 消失。两臂 payload 产物对齐：control 与臂 2 均 4 个 `_payload.json`（R50 的 `payloadExtraction:false` 形态 11→7 与此互证）。
