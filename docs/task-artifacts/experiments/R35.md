## 结论

**❌ R35 判负（阴性确认）：根 `vercel.json` 不可能覆盖对方 Project 的设置，F38 的交叉污染在当前架构下不可复现。**

机制（实证）：

1. **配置发现**：`vercel deploy --dry --debug` 日志显示 CLI 先 `Found config in file "...\<sandbox>\vercel.json"`（在 cwd 找到根配置），
   紧接着 `Read local config from root directory (apps/docs)`（**项目配置改从 Root Directory 读取**）。
2. **覆盖无效**：`vercel pull --environment=production` 把 Project 设置读回沙箱，`buildCommand` / `outputDirectory` / `rootDirectory`
   **全部保持原值**，根 `vercel.json` 声明的值（`R35-ROOT-BUILD-COMMAND` / `R35-ROOT-OUTPUT-DIR`）**未生效**。
3. **根配置仍会进源码树**：dry-run 的 file tree 同时列出 `vercel.json` 与 `apps/docs/vercel.json`——根配置被**当作普通源码文件上传**，
   而不是项目配置。

⇒ 根 `vercel.json` 只在「该 Project 的 Root Directory = 仓库根」时才是项目配置。本仓 docs Project 的
Root Directory = `apps/docs`，api Project 的 = `apps/api`，**两者都不读仓库根** ⇒ F38 的历史事故形态在当前架构下不可能复发。

**诚实标注**：本结论是「结构判定 + 等价验证」，**不是** F38 原式复现（未做真实部署、未在云端观察构建被改写）。
它证明的是「根配置不生效」这一机制，而非「历史上那次污染为何发生」。

## 关键发现

1. **【FINDINGS #30】根 `vercel.json` 的作用域由 Project 的 Root Directory 决定，与仓库布局无关**——
   「仓库里有没有根 `vercel.json`」不是判据，「**该 Project 的 Root Directory 指向哪里**」才是。
   本仓两个 Project 都设了 Root Directory ⇒ 根配置对二者都只是普通源码文件。
2. **【FINDINGS #30】F38 的既有治理决策（不做根 `vercel.json`）在本架构下是冗余的**——
   它是**历史事故的遗留防御**，当前结构已使该事故不可复现。**不建议因此删除该决策**：
   一旦某个 Project 的 Root Directory 被改成仓库根，根配置就会重新生效；保留决策 = 保留对那种改动的防护。
3. **【FINDINGS #30】F39（单槽绑定）与 F38 是两个独立的失效面**——F39 仍是真实风险（同一目录反复 `vercel link` 会覆盖绑定），
   且**本轮验证未触碰仓库的 `.vercel/project.json`**（沙箱隔离），F39 的成立性不受影响。
