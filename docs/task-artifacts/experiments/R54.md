## 3. 结论（verified）

1. **F50 最后一环闭合（实测）**：N4 的 prerender 执行使用**独立的内存态 storage 实例**——预热数据（裸 markdown）经序列化注入**可读**（keys 含 4 条），fs 驱动**未生效**（`write→readBack` 成功但双 buildDir 零文件、`node_modules/.cache/nuxt` 从未创建），content 的回写（`storage.js:163`）只进该内存实例、**随构建结束消亡**；主 bundle 的 `_snapshot` 读 fs 挂载（指向从未创建的新 buildDir 目录）→ 空 → bundled 零条。**「回写 → 快照」双向断裂**，写丢失去向 = **内存实例随构建消亡**（非写到别处——全盘无痕实锤）。
2. **N3 对照（实测）**：prerender 同为主进程 in-process（pid 一致），但 storage **fs 驱动直连**（probe 文件落盘 `.nuxt/content-cache/` 实锤）→ 回写落盘 → `_snapshot` 读到 → bundled 5 条 → 全链通。
3. **prerender 执行模型定案（实测 + 推断分界）**：双世代 prerender 均**主进程 in-process**（pid 实测；nitro 的 `#initWorker` 是 dev 模式 worker，无关）。**实测**：N3 执行体 = `.nuxt/prerender` 独立 bundle（报错栈 `nitro.mjs:3913`）；N4 执行体 = 探针所在环境（内存态 storage）。**推断（显式登记）**：N4 的 init#1（R52 观测，旧 buildDir）与 prerender 执行环境的实例拓扑未逐一定性——不影响「N4 prerender storage 内存态 + `_snapshot` 读 fs」的核心结论（两点均实测）。
4. **附带实锤（工具链）**：`defineNitroPlugin` 在 prerender bundle 中**不可自动导入**——nitro 插件需在 prerender 生效必须显式 `import … from "#imports"`（A 轮首跑 exit 1 的教训，写入证据）。
5. **F50 证据链完整度**：R52（base 错位 → `_snapshot` 读空）+ R54（回写进内存态实例）⇒ **双向断裂全实测**——上游 issue #36792 的答辩弹药完整（维护者问「为什么 setItem 没落盘」的答案 = 内存态 prerender storage）。
