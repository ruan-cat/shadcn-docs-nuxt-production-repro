## 结构性取证：为什么不是字面「拦截并改写该 key」

R48 分支构建产物 `apps/docs/.nuxt/prerender/chunks/_/renderer.mjs` 的字节级证据：

```js
108: const NUXT_PAYLOAD_EXTRACTION = true;
188: const payloadCache = useStorage("internal:nuxt:prerender:payload") ;   // ← 模块作用域解析
331: const _PAYLOAD_EXTRACTION = !ssrContext.noSSR && (NUXT_PAYLOAD_EXTRACTION);
390: await payloadCache.setItem(ssrContext.url === "/" ? "/" : ssrContext.url.replace(/\/$/, ""), …);
```

- 校验位于 unstorage 1.17.6 `prefixStorage` 包装器**内联**（`itemKey` 在委托 driver 之前抛错）⇒ nitro 插件、自定义 driver、根 storage 补丁都在校验**下游**，拦截不到。
- `payloadCache` 由生成 renderer 的**模块作用域** `useStorage()` 创建，且 `prefixStorage` 每次调用返回新对象 ⇒ 插件侧拿到的实例与 renderer 持有的实例**不是同一引用**，无法替换。
- unstorage 1.17.6 未提供绕过该校验的 API / 钩子。
- ⇒ **唯一可达的应用层路径 = 消除调用点本身**：`experimental.payloadExtraction: false` 让生成器把 `NUXT_PAYLOAD_EXTRACTION` 置 false，模板把 ：386 写入分支整体裁剪。

## 结论

**✅ R50 规避方向 C 验证通过（verified）——但形态必须订正：在 unstorage 1.17.6 的 API 面内，「应用层拦截并改写该 key」结构性不可达；可行的应用层形态是「关闭 payload 抽取，消除非法写入调用点」，同样完全规避 R46 的 prerender 500。**

- 构建全绿（Prerendered 11 → **7** routes：3 页面 + 2 ipx + 1 i18n + content-index，**4 个 payload 文件消失**）、探针 13/13（含指纹路由内容级断言）、closure exit 0、首页 SSR 完好。
- 机理链闭合：配置 → 生成器常量（`NUXT_PAYLOAD_EXTRACTION = false`）→ 模板裁剪写入分支 → 非法 key 的 setItem **调用点不存在** → 校验无从触发。

## 关键发现

1. **【FINDINGS #33】方向 C 的可行形态与代价**：`payloadExtraction: false` 的语义代价 = 客户端导航不再有预渲染 `_payload.json`（payload 请求改走运行时 SSR 兜底）。本仓生产验收面（content API 内容断言 + must-404 反向断言 + 首页 SSR）**全部不受影响**；若产品形态需要静态 payload，则只能选方向 A（[R48.md](./R48.md) 钉 unstorage，全保真）。
2. **【FINDINGS #33】「拦截改写」类规避的通用判断法**：当校验位于**包装器内联**（校验先于 driver 委托）、且被校验引用由**生成代码模块作用域**持有时——插件 / driver / 运行时 monkey-patch 三层全部不可达；唯一入口是把「触发写入的配置常量」关掉。该判断法适用于一切「生成代码 + 内联校验」组合的规避设计。
3. **探针纪律再兑现**：本实验同时跑了 `probe:content`（13 项）与首页 SSR 字节断言——因为 payload 抽取理论上可能波及首页（它正是唯一非法 key 的来源路由）；**变量 touching 哪条路由，哪条路由就要有专属断言**（F47/F49 家族纪律的推广）。
