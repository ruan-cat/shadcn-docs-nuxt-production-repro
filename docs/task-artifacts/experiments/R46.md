## 根因取证（字节级）

### 1. nitro 2.13.5 的唯一依赖增量

`nitropack@2.13.5/package.json`：`"unstorage": "^1.17.6"`（2.13.4 为 `"^1.17.5"`）。
nitro 自身在「bundled storage 注入 / storage 解析 / snapshot」全链路上，两版**逐字相同**
（`createStorage` / `snapshotStorage` / `_snapshot` / `buildProduction` / `rollup storage()` / `resolveStorageOptions` 全部一致）⇒ **nitro 自身无责**。

### 2. unstorage 1.17.6 给 `prefixStorage` 加了 key 校验

`unstorage@1.17.5/dist/shared/unstorage.zVDD2mZo.mjs:86-97`：

```js
function prefixStorage(storage, base) {
  base = normalizeBaseKey(base);
  if (!base) { return storage; }
  const nsStorage = { ...storage };
  for (const property of storageKeyProperties) {
    nsStorage[property] = (key = "", ...args) => (
      storage[property](base + key, ...args)   // ← 无校验
    );
  }
```

`unstorage@1.17.6/dist/shared/unstorage.lWbgcyKt.mjs:92-105`：

```js
function prefixStorage(storage, base) {
  if (base?.includes("?")) { throw new Error(`[unstorage] Invalid base: ${JSON.stringify(base)}`); }
  base = normalizeBaseKey(base);
  if (!base) { return storage; }
  const itemKey = (key) => {
    if (!normalizeKey(key)) {
      throw new Error(`[unstorage] Invalid key: ${JSON.stringify(key)}`);   // ← 新增
    }
    return base + key;
  };
  …
    nsStorage[property] = … async (key = "", ...args) => (
      storage[property](itemKey(key), ...args)   // ← 走校验
    );
```

### 3. `"/"` 恰好被判为非法 key

`unstorage@1.17.6/…:138-143`：

```js
function normalizeKey(key) {
	if (!key) {
		return "";
	}
	return key.split("?")[0]?.replace(/[/\\]/g, ":").replace(/:+/g, ":").replace(/^:|:$/g, "") || "";
}
```

`"/"` → `":"` → `""` ⇒ **falsy** ⇒ `itemKey("/")` 抛 `Invalid key: "/"`。

### 4. 观测到的 500 堆栈（原文）

```plain
[request error] [unhandled] [GET] http://localhost/
  [unstorage] Invalid key: "/"
    at itemKey (…/unstorage@1.17.6/…/unstorage.lWbgcyKt.mjs:102:13)
    at nsStorage.<computed> [as setItem] (…/unstorage.lWbgcyKt.mjs:113:25)
    at Object.render (apps/docs/.nuxt/prerender/chunks/_/renderer.mjs:390:22)
```

⇒ nitro prerender 期写根路由 payload（key = `"/"`）时命中该校验 ⇒ **prerender 500 ⇒ 构建失败**。

## 结论

**✅ R46 阳性复现（阻断级，构建级失败）——根因在 nitro 2.13.5，且精确到 `unstorage@1.17.6` 的 key 校验收紧。**

- 单变量（只 bump nitro 2.13.4 → 2.13.5、其余全不动）即在 **Nuxt 3.21.2 世代**触发 `Invalid key: "/"` ⇒ prerender 500 ⇒ 构建失败。
- ⇒ **R45 的判负归因需要修正**：R45 把判负点归给「Nuxt 4 世代整组迁移」，但本实验证明 **nitro 2.13.5 一个包就足以引入故障**，
  Nuxt 4 只是**让同一个缺陷换了一种表现**（见下）。

### R45 的「内容库为空」与本实验的「prerender 500」是同一个缺陷的两种表现

|                                         | control（nitro 2.13.4 / unstorage 1.17.5）                     | R46（nitro 2.13.5 / unstorage 1.17.6，Nuxt 3） | R45（nitro 2.13.5 / unstorage 1.17.6，Nuxt 4）                        |
| --------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| `prefixStorage.setItem("/")`            | 允许（无校验）                                                 | **抛错，未被 catch 包裹** ⇒ prerender 500      | 抛错**但被吞掉** ⇒ 内容库为空                                         |
| content 缓存位 `cache:content:parsed:*` | 被运行时回写成 `{parsed, hash}` **JSON**                       | 同左（构建已失败，未到这一步）                 | **停留在 `build:before` 写的裸 markdown**                             |
| `_snapshot` 抄到的内容                  | JSON                                                           | —                                              | **裸 markdown**                                                       |
| 生产运行时 `getContent`                 | `isProduction && cached` ⇒ `return cached.parsed` ⇒ **有内容** | —                                              | `cached` 是 markdown ⇒ `cached.parsed === undefined` ⇒ **内容库为空** |
| 症状                                    | ✅ 正常（探针 13/13）                                          | ❌ 构建失败（prerender 500）                   | ❌ 构建成功但**内容库为空**（探针 9 项 FAIL）                         |

**关键吞异常点**（`@ztl-uwu/nuxt-content@2.13.9/dist/runtime/server/storage.js:163`）：

```js
await cache.setItem(id, { parsed, hash }).catch(() => {});
```

R45 世代里这个 `.catch(() => {})` 把 `Invalid key` **静默吞掉** ⇒ 运行时解析结果永远写不回缓存位 ⇒
缓存位停留在 `build:before` 写下的**裸 markdown** ⇒ 生产运行时 `cached.parsed === undefined` ⇒ 内容库为空。

## 关键发现

1. **【FINDINGS #32】R45 判负的真实根因是 `unstorage@1.17.6` 的 key 校验收紧（经 nitro 2.13.5 引入），不是「Nuxt 4 世代」本身**——
   R46 用单变量（只 bump nitro）即在 Nuxt 3 世代复现故障 ⇒ Nuxt 4 迁移的变量面可**大幅缩小**：
   「Nuxt 4 迁移」的可行性与 nitro 2.13.5 的兼容性**必须分开评估**。
2. **【FINDINGS #32】content v2 用 `"/"` 表示根文档，与 unstorage 1.17.6 的 key 约定直接冲突**——
   `normalizeKey("/")` 归一为空串 ⇒ 被判非法。上游 content 与上游 unstorage 的**契约缺口**，
   两边都无辜但组合即坏。
3. **【FINDINGS #32】「静默吞异常」把构建期失败降级成了运行时数据缺失**——
   content 的 `.catch(() => {})`（`storage.js:163`）使同一个 key 冲突在 R45 里表现为「构建全绿 + 内容库为空」，
   在 R46 里表现为「构建直接 500」。**同一个根因、两种表象**，只取决于该 `setItem` 调用点是否被 catch 包裹。
   ⇒ 验收纪律再次兑现：**build 绿 ≠ 内容有**（与 F47 的「200 假阳性」同源，但更隐蔽：这里连状态码都是绿的）。
4. **【FINDINGS #32】可操作的规避方向**（不在本实验范围内，未验证）：
   - 钉住 `unstorage` 到 1.17.5（与 nitro 2.13.4 同代）；
   - 或升级 content 到规避 `"/"` key 的版本；
   - 或在应用层拦截并改写该 key。
     三者都需要独立实验验证，本实验只做到「根因定位」。
