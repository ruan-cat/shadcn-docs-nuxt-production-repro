## 结论

✅ verified —— 按 SOP 干净重测，`experiment/r15` 分支（精确 externalize Element Plus）install / build:packages / docs build 全绿（exit 0），standalone `.output` 可启动 `Listening on http://[::]:3000`，但**真实首页请求返回 HTTP 500**，响应体为 `Cannot find package '@popperjs/core' imported from .../apps/docs/.output/server/node_modules/element-plus/es/hooks/use-popper/index.mjs`。即该变量在干净环境下**真实复现 F17**：externalize Element Plus 后，其 `@popperjs/core` npm alias 链（`npm:@sxzz/popperjs-es`）在 Nitro standalone 产物中未保留，element-plus 的 use-popper hook 在运行时无法解析 `@popperjs/core`。

**判读**：与 R06/R07/R08/R10/R12（干净全绿、首轮失败纯属污染伪信号）不同，R15 在干净环境下**并非全绿**——其真实效应是**运行时依赖解析故障**，正是 PR #21（F17）所声称的故障。首轮 `exit 1 + Invalid URL` 虽为污染态伪信号（build 阶段失败，非变量本身问题），但干净重测揭示该变量确实触发 F17，故结论为"真实复现"，而非"判废"或"阴性"。这与总检报告 §3.1 仅判定"首轮结果不可信"一致——首轮不可信，但 Clean 重测给出的是**有效阳性**结果。

## 关键发现

- **R15 是系列中首个"干净态真阳性"**：R06–R12 干净重测均全绿（阴性），R14 为默认 heap OOM（资源约束型，8 GiB 下绿），R15 为**运行时依赖故障（阳性）**——externalize Element Plus 破坏 `@popperjs/core` alias 链（F17）。
- **污染伪信号 vs 真实阳性的区分纪律**：首轮 `exit 1 + Invalid URL` 是 build 阶段污染（应判废），但判废的是"首轮结果"而非"变量结论"；Clean 重测必须在 build 通过的前提下继续做到**运行时内容断言**，否则会像首轮一样漏掉 runtime 故障——本例若只在 build 绿处停手，会误判为阴性。
- **SOP 冒烟必须做内容/运行时断言**：本系列前序 R06–R12 因恰好是阴性（build 绿即 200）而掩盖了该风险；R15 证明"build exit 0 + Listening"不足以判定通过，必须 curl 真实路径并校验响应体（本例 500 + 具体错误）。
- **安全提醒（无关变量）**：恢复 main 时 `pnpm install` 的 `apps/docs prepare`（`nuxt prepare`）仍可能因 WorkBuddy 沙箱 `node-safe-delete-shim` 拦截批量删除 `.nuxt/dist`（>50 文件）而报 `ELIFECYCLE`；预移走陈旧 `.nuxt` 后重装 `exit 0`。属环境守卫，非实验结论影响因素。
