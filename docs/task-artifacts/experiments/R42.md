## 关键发现

1. **顺序不是变量，产物差异也不是顺序差异**：R42↔R43 三个配对（R42↔R43、R42↔R44、R43↔R44）的 docs 残差**签名完全一致**（恒为 6 个文件：1 个携带指纹的 client chunk + `styles.mjs`(+map) / `client.precomputed.mjs`(+map) / `server.mjs`），且这 5 个同名文件**归一化后长度相等、字符多重集相等**（`styles.mjs` 进一步逐行排序后相等）→ 属「同内容、异顺序」的**置换**；差异来源是构建内生的枚举顺序不确定性，**与顺序/并发无关**。
2. **api 侧对顺序完全免疫**：三轮 api 产物（`apps/api/.output`）**逐字节相同**（`index.mjs` 均 62116 B、非 volatile 文件哈希零差异、路由表 `/v1/**` `/v1/health` `/v1/runtime` 三条一致）——api 构建只依赖 `@repro/shared-core`，docs 的构建产物不进入其输入图，故顺序不构成变量。
3. **题面「4 项合取」在 docs 侧不可达（字面判据）**：排除 volatile 后仍无法做到哈希一致——原因不是 volatile 列表不全，而是 **161 个 `public/_nuxt/<contentHash>.js` 文件名本身由构建指纹派生**，且 chunk 内部互相引用兄弟 chunk 名 → 指纹一变，文件名与内容同时变（级联）。故本轮采用**分层判据**（原始 / 文件名归一 / 指纹归一 / 指纹+chunk 名归一 / 顺序归一），并在 evidence 中**如实标注字面合取 FAIL**、同时给出内容等价 PASS。
4. **题面采样器的 `repoCount` 口径在本机恒为 0（探针口径失效，已修正）**：本机 node 位于 `D:\store\nvm-desktop\22.23.1\node.exe` 与 `C:\Users\pc\.nvmd\bin\node.exe`，**在仓库之外** → 题面按 `Path -like '*shadcn-docs-nuxt-production-repro*'` 识别「本仓进程」永远命中 0 个；已补建 CIM CommandLine 口径采样器（本仓 node 进程数 / WS 合计 / 单进程 WS 峰值），否则 R44 的「并发确实发生」将无法取证。
