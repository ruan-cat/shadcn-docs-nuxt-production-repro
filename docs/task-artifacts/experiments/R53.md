## 3. 结论（verified）

1. **双平台产物内均无 workspace symlink**（F41 的核心风险面排除）：`.output/server/node_modules/@repro/` 两平台都不存在——`@repro/shared-core` / `@repro/ui` 被 **bundle 内联**进 chunks，不以 symlink 形态进产物。R38 关注的「workspace `*` symlink 指向 Root Directory 之外」的风险面**在产物内不存在**（R34 云端运行时断言通过的机理确认）。
2. **产物内 symlink 形态的平台差异（实锤）**：Windows 的 `node_modules` 顶层包为**实体目录**，`.nitro` 类型目录与嵌套依赖（`mdn-data`、`@vue/devtools-api`、`@vue/shared` 等）为 symlink；Linux 同位全部 symlink。**关键差异在 symlink 的目标形态**：
   - **Linux**：`css-tree -> .nitro/css-tree@2.3.1`（**相对路径**，21 字节——standalone 可移植）；
   - **Windows**：`css-tree -> /d/code/…/node_modules/.nitro/css-tree@2.3.1`（**构建机绝对路径**，110 字节——**换机启动即断**）。
   - 与 [R22](./R22.md) 的发现同族（R22：`trace:false` 产物依赖写成 `file://` 构建机绝对路径 → 换机即崩）——**Windows 构建产物内的链接类引用默认不可移植**是本仓的双平台结构性事实（默认 trace 与 trace:false 两种形态下都成立）。
3. **F41 判读**：Windows vs Linux 的 symlink 差异**真实存在且方向确定**（Windows 绝对 / Linux 相对），但在**默认 trace + 本机/同机运行**场景不触发故障（绝对路径自洽）；风险仅在「Windows 构建 → 异机部署」场景（生产部署走 Vercel/CF 的 Linux 构建，不经 Windows 产物）⇒ **当前架构下 F41 维持「控制组已观察（平台差异定性完成），无运行时故障」**。Linux closure（`probe:closure`）由本仓 CI 持续被动观察 + 本实验 artifact 结构审计双重覆盖。
4. 顺带登记：`workflow_dispatch` 的 GitHub 规则——**workflow 文件必须先存在于默认分支**才能对其他 ref dispatch（首试 HTTP 404 的根因）。
