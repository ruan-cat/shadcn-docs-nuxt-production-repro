## 结论

✅ **R22 判定：verified（阳性复现）。`nitro.externals.trace = false` 在 Linux 生产构建链上同样破坏 standalone 产物的自包含性——构建成功，但 `.output/server/package.json`（standalone manifest）与 `.output/server/node_modules`（拷贝层）均不生成。**

1. **首个失败门明确 = G5 产物自包含门**：`probe:closure` → `Error: 缺少 docs standalone manifest: apps/docs/.output/server/package.json` → **exit 1**（`probes/inspect-artifact-closure.ts:78`）。
2. **构建本身全绿**：`Tasks: 4 successful, 4 total` / `Cached: 0 cached, 4 total` / `Time: 1m14.848s` / `✨ Build complete!` / `Nuxt Nitro server built`。⇒ **只看 build 退出码会 100% 漏检**——这是 F18「build 绿但 `.output` 不可运行」的又一阳性样本。
3. **提速收益在 Linux 上几乎不存在**：R22 `1m14.848s` vs control `1m18.339s` = **仅快 3.5 秒**；而 R21 在 **Windows** 上报告「快 ~133s」（213s → 79.8s）。⇒ **`trace:false` 的构建提速收益高度依赖平台**，Linux 上可忽略。
4. **机制自洽**：依赖被 `external: true`（chunk 普遍变大 3.5%–124%，见上表）→ 需要外部 `node_modules` → 但 trace 被关闭导致拷贝层不生成 → **依赖既没被 inline、也没被拷贝** ⇒ 运行时缺包是必然的（CI 未走到运行时门，见「遗留验证项」）。

### ✝️ 对既有结论的两处订正（这是 R22 的主要价值）

- **订正 R21 的「F26 缺包链未触发」**：R21 的判读只检查了「产物零裸导入」（静态 `from` / 动态 `import()` / `require` 三类扫描全空），**并未执行 `probe:closure` / `probe:artifact`**——而这两个探针需要 `.output/server/package.json`，在 `trace:false` 下**根本不存在**。⇒ R21 的「缺包链未触发」是**证据不足导致的假阴性**，不是「trace:false 安全」。R22 证明：在 Linux 上，`trace:false` 破坏的是**产物自包含性**（manifest + 拷贝层双缺），比 R21 观察到的「拷贝层消失」更早、更硬。
- **订正 FINDINGS #13 的「R22 价值下降，建议重估优先级」**：该判断已**被本实验推翻**。R22 有明确价值，且产出的是**阳性**信号而非 null：「`trace:false` 的收益（构建时长）在 Linux 上可忽略（-3.5s），代价（产物自包含性破坏）是确定的」——**收益/代价比在 Windows 与 Linux 上完全相反**。

### ⚠️ 遗留验证项（未完成，不得当作已验证）

1. **运行时是否真 500 尚未实测**：CI 在 `probe:closure` 就 exit 1，**未走到** `probe:artifact` / `probe:content`。缺包链的**运行时签名**（`Cannot find module` / `Cannot find package`）仍需在**隔离父级 node_modules** 的 standalone 产物上实测才能闭环。**本机验证需等 R42–R44 完成**（并发跑 3.5 GiB 构建会污染其内存水位测量，F43）。
2. **R21 与 R22 的配置路径未经字节级确认一致**：`experiment/r21-windows-only-trace-false`（`d7a0113`）**仅本地、未推送**，其 reflog 显示只有 1 个提交，但**该提交实际改了哪几个文件、改的配置键路径是否同为 `nitro.externals.trace`，在本轮无法字节验证**（取证时只能由「档案自述 + nitropack 源码 + 契约字面」三条间接证据重建）。若 R21 实际写的是 `nitro.trace`（顶层）或其它路径，则 **R21 与 R22 的行为差异可由此完全解释**，无需引入平台差异假设。⇒ **R21 与 R22 的对照结论在 R21 字节级复核前应视为「待解释」，不得写成「Windows 与 Linux 行为不同」。**

## 关键发现

1. **F26 的真实触发面比 R21 描述的更宽**：`trace:false` 的破坏不止是「拷贝层变小」，而是 **standalone manifest 与拷贝层双缺** ⇒ probe 直接拿不到产物清单，运行时也拿不到依赖。**「build 绿」与「产物可用」在此彻底分离。**
2. **`trace:false` 的收益具有强平台依赖**：Windows -133s vs Linux -3.5s。⇒ 若有人以「Windows 上快 133s」为依据推广该 workaround 到 CI/生产，结论会完全站不住。**这是「Windows workaround 不可复制到生产」的硬证据**（正是 R22 单变量的原始意图：「证明生产环境不能复制 Windows workaround」）。
3. **R21 的假阴性机制可复用为通用教训**：当探针依赖某个**由被测配置本身决定是否产出**的文件时，「探针提前 exit 1」与「故障未触发」是**两件事**，必须分开记账。本例中 R21 若跑 `probe:closure`，会立刻暴露问题，而不是给出「零裸导入 ⇒ 安全」的错误结论。
4. **CI 侧的 `probe:closure` 起到了「首个失败门」的作用**：它在产物自包含性被破坏时**立即失败并给出精确路径**，比等到运行时 500 更早、更可诊断。该探针的存在价值在本实验中得到实证。
5. **本仓 `trace:false` 的净收益为负**：Linux 侧收益 -3.5s（≈5%），代价是产物自包含性确定被破坏 ⇒ **不应引入基线**（与 F38 同类治理逻辑：不得用「Windows 上有效」的单平台证据引入跨平台风险）。
